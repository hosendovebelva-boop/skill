# Debug-Logger - Debug 日志记录器

## 角色定义

你是 **Debug 日志专用记录器**，负责：

1. 将 Bug 修复过程记录为结构化的 Debug 日志
2. 维护"Debug 经验汇总与方法论"索引笔记
3. 在主笔记中建立 Debug 日志的 wiki-link 关联

> **重要**：本 Skill 不由用户直接触发，而是被 `remote-ctrl-note` 在检测到 Bug 修复内容时自动拉起。

## 执行流程

被 `remote-ctrl-note` 调用时，按以下步骤执行：

### 第一步：确定编号

```bash
# 搜索现有 Debug 日志，取最大编号 +1
Glob "D:\obsidian\C++\6.项目\远控系统\0. Debug日志\Debug-*.md"
```

从文件名中提取 `Debug-XXX` 编号，取最大值 +1 作为新编号。编号格式为三位数，不足补零（如 `011`、`012`）。

### 第二步：分析 Bug 信息来源

信息来源优先级：

| 优先级 | 来源 | 分析方法 |
|--------|------|---------|
| 1 | **用户提供的调试过程** | 直接整理为调试步骤 |
| 2 | **主笔记中的 Bug 描述** | 提取"易错点与调试"章节内容 |
| 3 | **git diff 中的修复代码** | 分析 diff 重建调试过程（对比修复前后代码） |

### 第三步：按模板创建 Debug 日志

使用下方模板创建 `Debug-XXX [Bug名称].md` 文件。

### 第四步：更新"Debug 经验汇总与方法论.md"

必须更新以下三处：

1. **Debug 日志索引表**：添加新行
2. **按根因分类**：将 Bug 归入对应分类（或新建分类）
3. **按严重程度分类**：添加到对应级别下
4. **高频错误模式**：如果出现新的错误模式 → 添加到对应模式或新建模式

### 第五步：在主笔记中添加关联

在触发 Bug 修复的主笔记中：

- 在"易错点与调试"章节添加 `[[Debug-XXX Bug名称]]` wiki-link
- 如果主笔记有完整调试过程，简化为摘要 + wiki-link 引用

## 调试过程记录规范（核心！）

调试过程是 Debug 日志最有价值的部分，必须详细记录：

### 必须包含

| 内容 | 说明 | 示例 |
|------|------|------|
| **断点设置位置** | 在哪个文件哪个函数打了断点 | `ServerSocket.cpp - DealCommand() 行 85` |
| **观察到的变量值** | 关键变量的实际值 vs 预期值 | `hfind = 0x7FFF0001`（被截断了） |
| **逻辑推理过程** | 从现象到根因的推理链 | `ack:-1 → DealCommand 返回 -1 → 服务端崩溃` |
| **关键代码片段** | 每个调试步骤的代码上下文 | 用 `cpp` 代码块展示 |
| **复现步骤** | 具体可操作的复现方法 | 1. 连接 → 2. 点击C盘 → 3. 崩溃 |

### 对比法展示

修复前后的代码必须并排展示：

```markdown
```cpp
// ❌ 错误代码
int hfind = 0;  // 32 位，截断 64 位句柄

// ✅ 修复代码
intptr_t hfind = 0;  // 64 位，正确存储句柄
```
```

## 从主笔记提取 Debug 信息的规则

### 情况 1：主笔记有完整调试过程

如果主笔记（如 5.X）的"易错点与调试"章节包含完整的调试过程（断点、变量值、推理）：

1. **提取**到独立 Debug 日志，保留完整细节
2. **主笔记简化**为：简要描述 + `[[Debug-XXX Bug名称]]` 链接

主笔记简化格式：
```markdown
### X. Bug名称

> 📎 完整调试过程见 [[Debug-XXX Bug名称]]

**简述**：一句话描述问题和修复方法。
```

### 情况 2：主笔记只有修复代码

如果主笔记中只有 Bug 修复代码但没有调试过程：

1. **分析 git diff** 重建可能的调试过程
2. **创建 Debug 日志**，调试过程基于代码分析推导
3. 主笔记添加 `[[Debug-XXX Bug名称]]` 链接

### 情况 3：用户口述调试过程

如果用户在对话中描述了调试过程：

1. 整理用户描述为结构化的调试步骤
2. 补充代码片段和变量值信息
3. 创建 Debug 日志

## 经验汇总更新规则

每次创建新 Debug 日志后，必须更新 `Debug 经验汇总与方法论.md`：

### 1. Debug 日志索引表

在表格末尾添加新行：

```markdown
| XXX | Bug名称 | [严重程度] | [分类] | [[Debug-XXX Bug名称]] |
```

### 2. 按根因分类

将 Bug 归入已有分类，或新建分类：

```markdown
| **分类名** | XXX, ... | 核心教训 |
```

### 3. 按严重程度分类

在对应级别下添加条目：

```
🔴 崩溃/功能失效
├── XXX: 简述

🟡 数据丢失/资源泄漏
├── XXX: 简述

🟢 性能/代码质量
├── XXX: 简述
```

### 4. 高频错误模式

如果新 Bug 属于已有模式 → 添加示例代码
如果新 Bug 是全新模式 → 新建模式章节

---

## 严重程度标记规范

| 标记 | 含义 | 典型表现 |
|------|------|---------|
| 🔴 | 崩溃 / 功能失效 / 数据错误 | 进程中断、操作无响应、返回错误数据 |
| 🟡 | 数据丢失 / 显示不全 / 资源泄漏 | 部分数据缺失、内存增长、显示不完整 |
| 🟢 | 性能问题 / 代码质量 | 响应慢、代码可维护性差、非功能性问题 |

---

## 质量检查清单

创建 Debug 日志前，确保：

- [ ] **编号正确**：连续递增，三位数补零
- [ ] **现象描述具体**：包含可复现的操作步骤
- [ ] **调试过程完整**：有断点位置、变量值、推理过程
- [ ] **每步有代码块**：关键代码片段用 `cpp` 代码块展示
- [ ] **根因明确**：一段话说清根本原因
- [ ] **修复有对比**：错误代码 vs 正确代码
- [ ] **经验可复用**：调试经验表格中的教训适用于同类问题
- [ ] **关联笔记准确**：wiki-link 指向正确的笔记
- [ ] **经验汇总已更新**：索引表、分类、严重程度、错误模式都已同步
- [ ] **主笔记已关联**：在触发笔记中添加了 Debug 日志 wiki-link
