# Note Creator

在 vault 里新建笔记。vault 根目录：`~/Documents/C++/obsidian_notes-main`。

**动手前先做两件事**：

1. 用 `note-locator` 或 Glob 搜一遍，确认这个主题没有已存在的笔记。有就问用户：扩展旧的（转 `note-extender`）还是新建。
2. `ls` 一下目标目录。`references/vault-map.md` 里的目录表随时可能过期，**以磁盘上的实际结构为准**。

笔记的组织方式、讲解深度、章节切分由你自己判断。下面只列你猜不到的约束。

---

## 硬性约束

**代码必须配讲解。** 这是本 vault 最重要的一条。禁止大段代码不加说明。每个代码块要说清「为什么这样写」而不只是「代码在做什么」。超过 30 行的代码拆成逻辑块逐段讲。

**C++ 代码严格 Modern C++**：

| 禁止 | 用 |
|---|---|
| `new` / `delete` | `std::make_unique` / `make_shared` |
| `NULL` | `nullptr` |
| C 风格数组 | `std::array` / `std::vector` |
| C 风格强制转换 | `static_cast` / `dynamic_cast` |
| 裸指针表达所有权 | 智能指针 |

**wiki-link 只链已存在的笔记。** 建链接前先确认目标文件在 vault 里。不要在末尾堆砌"相关笔记"清单 —— 链接要出现在它真正相关的那句话旁边，并写清关联理由。链接前置知识和深入阅读，不链"主题相近"。

**不编造。** 拿不准的内容标 TODO，别硬写。

---

## 示例代码配时序图

示例代码写完后，紧跟在代码块下面用 Mermaid `sequenceDiagram` 画出这段代码的执行时序。

- participant 写真实的执行主体：线程、进程、客户端/服务端、用户态/内核态、相互协作的对象。不要写 `main()`、`程序` 这类笼统名字。
- 消息文本用代码里真实的函数名（`pthread_cond_wait`、`epoll_wait`、`push`），不要写"调用函数"。
- **必须标出阻塞与等待区间**：用 `activate` / `deactivate`，或 `Note over X: 睡眠中`。谁在等、被谁唤醒，正是读源码时看不出来、需要图补上的信息。
- 图下面配一句话，点明这张图揭示了什么代码本身没写出来的东西。

**没有时间维度的代码不要硬画。** 只有一个执行主体的代码——语法演示、类型推导、模板特化、单一函数内的纯计算、容器 API 用法——画时序图只是把源码竖着重抄一遍。这类代码改用 `flowchart` 讲控制流，或者不配图。

## 力扣题解的额外规则

- 文件名 `{题号}. {中文题名}.md`，放进 `5.算法/5.3 力扣/` 下对应分类目录（`5.3.N 名称` 形式；目录不存在就建）。
- frontmatter 必须有：`tags: [算法, 力扣, 题解]`、`aliases`（英文题名）、`题号`（字符串）、`难度`、`阅读次数: 0`。
- 写完要回 `5.算法/5.2 算法/` 对应章节笔记的 `## 截图题目练习分配` 表格，在「引用」列补上 wiki-link。
- 代码用到 STL 容器/算法时，链到 `5.算法/5.1 STL/` 下对应笔记。

## 题目汇总（出题）的额外规则

风格对齐这两份标杆样卷，写之前读一份：

- `1.C++基础/6. 指针/6.10 指针题目汇总.md`
- `1.C++基础/7. 结构体 & 联合体/7.3 结构体与联合体题目汇总.md`

分层出题：基础题查「会不会」，场景题查「能不能用」，面试题查「能不能讲清楚」。答案里的「为什么」要写到能直接当面试口述稿。
